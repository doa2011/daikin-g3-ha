# 中文研发记录

## 2026-11-25：G3 第六页电子相册

- 基于上游 BRY88BBA15G RC6 文档，确认屏幕为 480×854、最多 8 个组合页面；远程换页使用 1 起始页码，指定第六页为 `screen.page.set {page:6}`。
- SCN3 已公开组件类型没有 JPEG 图片组件；上游媒体接口的 `screen.media.begin/chunk/commit` 上传 JPEG，`screen.push.send` 以定时媒体视图显示图片。当前实现采用“第六页作为底层常驻页面 + 定时媒体图片视图”，不修改用户 SCN3 布局。
- 增加切页确认：必须先确认第六页存在且启用，随后才处理图片上传；页面无效时不消耗媒体上传。
- 保留既有 EXIF 旋转、480×854 裁切、baseline JPEG、128 KiB 限额、512 字节分块、CRC/ACK、随机轮播及协作停止机制。
- 新增测试：切到第六页先于上传、页六禁用时拒绝且不上传、目录不存在。
- 实机尚待验证：实际 MCU JPEG 解码、屏幕显示、颜色裁切和连续轮播。

## 2026-11-26：连续相册第一轮

- 支持 screen.push.update 的设备采用同一通知 ID，旧图显示期间预传新图；到播放时间且上传成功后原位替换，确认 displayed 后释放旧图。旧固件保留原路径。
- 相册专用 JPEG 预算 64 KiB，先观察真实耗时；不修改通用媒体协议。停止时仅清理本会话。异常后保留旧图，显式停止可清理；固件最长一小时自动退出保护。
- 本轮仍为通知视图，不声称原生全屏。后续需独立页六原生显示、固件端解码失败保护、传输吞吐和传感器回归。

## 2026-11-26：原生第六页相册接入

MCU e410fe9 增加独立相册 ID 与全屏层；ESP32 95c9a36 提供 screen.album.set/clear，要求 MCU 状态协议 >=5。HA 双重能力识别后优先采用 NativeAlbum，预传新图、ACK 后释放旧图，不强制换页，不进通知队列。普通消息和摄像头通知不主动停止原生相册；旧固件保留原路径。亮度/唤醒沿用设备全局策略，原生专用亮度尚待实现。ACK 表示解码成功而非 LCD 实际扫描确认。需三端匹配测试，不作为实机验收。

## 2026-11-26：OTA 与原生相册联合候选修正

- 联合候选同时锁定 MCU 原生相册/OTA 退出恢复、ESP32 OTA 电源租约/原生相册协议，以及 HA 原生相册播放器。
- 实机状态日志曾显示第六页已启用但当前页为 1；MCU 原生图层只在 page==5（API 页码 6）时显示。原 NativeAlbum 仅检查第六页 enabled_mask，却没有切换页面，因此即使 MCU 与 ESP32 协议都支持，照片也可能被解码但不可见。
- 修正 NativeAlbum：首次呈现前保存当前页并等待 screen.page.set 到第六页的 MCU ACK；后续换图检测用户是否手动离页，不强行抢回；停止时仅在当前仍为第六页的情况下恢复原页面。解码失败保持旧图，清理失败保留资源所有权供 stop_album 重试。
- AlbumPlayer 在任务终止时统一关闭本会话，避免解码失败后遗留 album_id 或页面状态。
- 新增测试覆盖自动切第六页、恢复原页、手动切页优先、禁用页拒绝、已在第六页时不改页。
- 这仍是 CI/宿主测试；未获得实机 LCD 帧扫描确认，不能把 MCU 解码 ACK 当作物理显示 ACK。
